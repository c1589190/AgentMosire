## Goals / Non-Goals

**Goals**

- 明确三模块接口、状态所有权和运行路径。给 Java 嵌入和 Main 运行提供同一套授权、窗口和父子请求语义。
- 用外部插件兼容性测试固定宿主契约。用多个真实父子进程验证执行身份、暂停恢复和异步回复归属。

**Non-Goals**

- 首期的交付边界为三模块本地构建和验收。BashPlugin、Workspace、Docs、Search 及发布流程属于后续工作。

## Decisions

### 模块与宿主

**用户裁定**见[迁移命名](#原话-1-迁移与命名)、[首期边界](#原话-2-首期范围和上下文分层)及 [PF4J](#原话-3-统一-pf4j-宿主)。

| 模块 | 所有权 | 调用方向 |
| --- | --- | --- |
| AgentLib | 单条消息、内容片段、模型调用、工具与资源声明、权限和决策数据契约 | 向上层和插件作者提供公开类型 |
| Brain | 会话历史和窗口、Agent 循环、默认与可替换压缩、上下文注入、有效权限判定、草案和父子请求状态 | 使用 AgentLib 契约，提供 Java 嵌入入口与宿主接线端口 |
| Main | 配置读取、进程启动和 stdio 传输、统一 PF4J 管理、父子工具注册、服务接线 | 以 Brain 为运行时，使用 AgentLib 契约向插件提供宿主服务 |

**设计建议**采用 Java 21 和 Maven，将 Maven `groupId` 与 Java 包前缀统一为 `io.github.c1589190`。各仓模块产出单独 JAR，Main 可以提供携带依赖的可执行形态。Main 管理兼容性检查、依赖顺序、登记、停用与回收。工具插件依赖宿主共享 API，按扩展声明供应工具。Brain 的授权检查适用于已加载插件，安装插件的权限归宿主操作者。旧包名编译的调用方和插件切换时更新坐标和引用并重新编译。

**内置工具建议**保留按权限过滤的 `tool_catalog` 和按提出者读取的 `decision_history`。裁决和提交通道向获授权的角色开放。派生、列表与等待在启用子 Agent 编排时注册，终止和读取上下文分别授权。父子桥的内部传输入口由运行时持有。具体首期清单尚未逐项裁定。

### Agent 上下文

**用户裁定**见[原话 2](#原话-2-首期范围和上下文分层)。

Brain 接管当前的窗口、组请求、写回、压缩和注入。AgentLib 提供 `LlmMessage`、`ContentPart` 等元素和模型调用契约。Brain 向宿主开放现有 Builder 一类的策略接入入口，默认压缩策略与替代策略共用同一个窗口生命周期。Main 提供模型与容量配置。

**设计建议**由 Brain 分别构建模型请求输入和会话写回输入。父级异步回复在压缩后、下次模型请求前加入。请求成功后确认该次模型投递，失败则保留待投递状态。持久回执记录与消息历史有独立用途。原仓目前把附有注入的输入整批交给 `LlmRoundTrip` 写回，迁移时用提交后一轮、模型失败重试和重启回放验证矫正后的行为。

### 工具授权和资源

**用户裁定**见[权限规则原话](#原话-4-工具鉴权与父级代执行)、[身份档位原话](#原话-5-三档身份和执行中提交)及 [READONLY 覆盖规则](#原话-7-readonly-的白名单覆盖)。

1. 各工具模块维护本工具的权限组规则、资源定义和触碰条件，Brain 负责统一判定与执行。身份档位固定为 `READONLY`、`DEFAULT`、`SYSTEM`。
2. Agent 显式配置的 `Allow`、`Ask`、`Block` 在同一层应给同一工具一个明确结果。白名单和黑名单冲突属于配置错误。权限组归属先按身份默认值，再应用显式配置。
   `READONLY` 提供默认分组。显式白名单可将写操作工具归入 `Allow`，仍须满足父级授予和资源规则。
3. `Allow` 适用父级授予的资源范围，受到限制的访问按父级策略返回拒绝或转 `Ask`。工具模块负责在副作用前识别具体访问。若工具触碰多个资源，设计建议整次调用先判定，存在 `Block` 就拒绝，否则存在 `Ask` 就提交草案。
4. `Ask` 生成草案，`Block` 结束调用。子级直调范围按有效权限逐级求子集。递交草案保留提出者身份，实际执行主体使用自己的有效权限和资源约束。显式拒绝按该层规则生效。

**设计建议**在每次调用先固定同一个工具实例用于鉴权和执行。工具的资源观察或参数解析应在作用生效前完成。父级代执行时重新解析实际要触碰的资源，避免用草案描述代替自身授权判定。

### 执行中向父级提交

**用户裁定**见[原话 4](#原话-4-工具鉴权与父级代执行)和[原话 5](#原话-5-三档身份和执行中提交)。

    子 Agent 当前草案或问题 → Main 父子链路 → 父 Agent 待处理请求
    父 Agent 裁决 → 以父级有效权限执行获批条目 → 按请求编号回传逐项结果
    Brain 子级运行时 → 恢复等待任务，或在下次模型请求前注入异步回复

| 阶段 | 状态与所有者 |
| --- | --- |
| 草案 | 子级 Brain 持有可追加草案，查看时提供快照。提交时封存本批，后续调用进入下一批。问题与非空草案至少提供一项。 |
| 请求与答复 | Main 从现有 stdio 链路接入，依据已绑定的进程身份路由给直接父级。父级 Brain 按请求编号受理、排队、裁决与执行，答复包含问题答案和适用的条目结果。 |
| 等待 | Brain 暂停发起请求的子任务，收到回执、取消或超时后交回明确结果。父级等待任何子任务时，直系子级新请求会唤醒父级运行循环。对同一运行时串行调度。 |
| 异步 | 受理回执带请求编号，子级可继续运行。Brain 按子级与会话投递回复。执行过程结束时可附结束摘要及尚未完成的请求编号。 |

**设计建议**由 Main 装配 `decision_pending`（当前草案）、`request_parent`（可选问题、是否提交当前草案、`wait` 或 `async`）和父侧 `reply_to_subagent`（答复与裁决）。这些命名用于说明接口职责。在回合收尾可提交尚未发送的草案与短结论。父级已有 `Block` 则拒绝，父级自己的 `Ask` 可以按它的配置继续向上提交。

## Risks / Trade-offs

- **等待环**。现有父侧等待只观察子级终态。加入父级请求到达的唤醒条件，保留一个父级运行循环，使用真实进程测试同时等待与恢复。
- **提交重试**。用绑定的提出者、请求编号及条目身份关联受理和回执。请求内容冲突时报错。已经执行并记录的条目复用结果，副作用结果不明的条目标记为待核验。
- **工具生命周期变化**。装载时校验来源冲突并批量登记。移除来源后，后续目录和调用统一生效。运行时校验与执行使用同一个工具实例。
- **历史与上下文混写**。异步回复投递和历史写回采用各自的输入视图，使用模型请求失败、重试、压缩和重启的组合场景验证。

### 原话 2 首期范围和上下文分层

> 我不认为应该迁移BashPlugin。因为插件规范也许需要调整。先迁移Agentlib、Brain和Main，提供一套标准的Agent运行时，带基本工具权限面鉴定、Agent决策包；Agentlib应当只声明基本上下文中的单一元素，应当把上下文压缩等对上下文整体进行调整的方法（即时里面只有一套非常简单的实现，它本来就可能需要被复写）上移到Brain，后续有上下文注入等，也是在Brain里写新模块，调整Agentlib提供的上下文元素，你应该把握其中的分层抽象关系；版本号可以调整为0.0.1-early；这是否可行？进一步设计工作流

### 原话 3 统一 PF4J 宿主

> 4不用着急，因为Main层还要维护统一的PF4J，也就是说，这三个模块若编译出独立jar文件，应当直接允许载入标准的任意插件，这是否也是可行的？；只有三个模块的话，Brain里面决定写入哪些基础命令？

其中第 4 项指此前工作流的早期发行包环节。Brain 的具体内置工具清单是设计议题，尚未逐项裁定。

### 原话 4 工具鉴权与父级代执行

> 协议疑似有点复杂了；其实最初我想设计的机制很简单，对于工具本身，只定义在这个工具下什么是资源面、何时触碰到什么资源面，对于单个Agent配置，定义其能随便用什么工具（Allow）、需要进决策包的可用工具（Ask）、不能用的什么工具（Block），身份等级就是前者默认的三级，黑名单就是其上额外的拒绝工具，白名单就是其上额外的允许工具（黑名单、白名单不可重合，因为同级），工具资源面又是另一回事，只有Allow组的工具允许定义资源面，如果这次工具调用面触及到相关限制资源面，可由父Agent设置是拒绝还是进决策包等通知；Readonly很显然是一个身份等级，之后的一切权限定义、代码设计都应遵循如此；你能否把握这样的设计？其中有一些要点，那就是首先，权限组规则和实现是由不同模块的AgentTool自己维护定义的，其次是，如果一个子Agent的某一工具被限制了权限面，那么其创建的进一级子Agent对应工具，要么权限面不得大于子Agent，要么干脆走Ask，让子Agent本体代为调用（决策包决策的本质其实就是子Agent提供调用草案，父Agent调用，然后再把结果统一回传子Agent）；这样的机制是否可行、目前是否是遵循如此？

### 原话 5 三档身份和执行中提交

> 现有身份档位替换为READONLY、DEFAULT、SYSTEM吧；然后就是决策包的向父Agent提交，众所周知，一般工作流是父Agent调用多个子Agent，然后子Agent搞搞工具调用，生成决策包，最后输出最终结论，把决策包和短期最终结论提交给父Agent——但是这样的调用流程似乎有点不灵活了，应当允许子Agent在执行中直接向父Agent提问/提交一次决策包，允许在父Agent响应之前不继续或是仅提交不阻塞、有结果后注入上下文两种方法，这要求Main至少提供一套子Agent查看当前决策包、向父Agent提交的同时提问（两者可缺1）的机制，这是否也是可行的？

身份档位以本条为准。阶段性提问、分批提交和两种等待方式扩展先前的回合收尾协作流程。
